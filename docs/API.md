# API reference (v1)

A **static** API: every endpoint is a plain file, so there is no server, no key and nothing to rate
limit beyond GitHub's own courtesy limits. It is regenerated by the daily workflow and committed, so a
`GET` is all you need.

## Base URLs

| base | CORS | notes |
|---|---|---|
| `https://raw.githubusercontent.com/mayankmohan1992/india-macro-war-room/main/api/v1/` | ✅ `access-control-allow-origin: *` | recommended for apps — verified header, works from a browser |
| `https://mayankmohan1992.github.io/india-macro-war-room/api/v1/` | ⚠️ same-origin friendly | mirror served by GitHub Pages; use it when you are already on that origin |
| `https://cdn.jsdelivr.net/gh/mayankmohan1992/india-macro-war-room@main/api/v1/` | ✅ | optional CDN mirror for lower latency |

Pin a commit instead of `main` if you need immutability:
`https://raw.githubusercontent.com/mayankmohan1992/india-macro-war-room/<commit-sha>/api/v1/latest.json`

Caching: files are static, so send `If-None-Match`/`If-Modified-Since` and let the CDN answer 304s.
The dataset changes at most once a day (see `status.json`).

## Endpoints

### `GET /index.json` — catalogue (start here)

One entry per indicator: identity, unit, kind, frequency, current status, latest reading and the paths
to its full history. Points and change logs are **not** included, to keep this file small.

```json
{
  "meta": {
    "api_version": "v1",
    "dataset_as_of": "2026-10-11",
    "dataset_as_of_by_frequency": { "daily": "2026-10-11", "weekly": "2026-10-09",
                                    "fortnightly": "2026-09-30", "monthly": "2026-09-30" },
    "retrieved_at": "2026-10-17T16:17:15Z",
    "indicators": 38,
    "source": "Reserve Bank of India — Database on Indian Economy (DBIE)",
    "source_url": "https://data.rbi.org.in/",
    "provenance": "Compiled from RBI public publications. Not an official RBI product: ...",
    "license": "Code: MIT. Data: compiled from RBI public publications, with attribution."
  },
  "indicators": [
    {
      "id": "cpi",
      "label": "CPI inflation",
      "unit": "%",
      "group": "Prices",
      "kind": "reading",
      "frequency": "monthly",
      "status": "watch",
      "status_reason": "4.82% - above target",
      "scoring_rule": "RBI flexible target 4% +/- 2% (2-6%). Green 2-4.5, ...",
      "series": "cpi_yoy",
      "source": "RBI r11 (CPI 2024=100)",
      "latest": { "date": "2026-08-31", "value": 4.82, "change": 0.37 },
      "stale": false,
      "definition": { "term": "Consumer Price Index (CPI) inflation, combined",
                      "source_url": "https://www.pib.gov.in/..." },
      "links": { "self": "series/cpi.json", "csv": "series/cpi.csv" }
    }
  ]
}
```

### `GET /latest.json` — every current value in one request

Keyed by indicator id. The cheapest way to render a scoreboard.

```json
{ "meta": { "...": "..." },
  "latest": {
    "cpi":  { "value": 4.82, "unit": "%", "date": "2026-08-31", "status": "watch",
              "change": 0.37, "kind": "reading", "label": "CPI inflation" },
    "repo": { "value": 5.5, "unit": "%", "date": "2026-10-06", "status": "bad",
              "change": null, "kind": "setting", "label": "Policy repo rate" }
  } }
```

`change` is the step from the previous reading (same unit as `value`). For a **setting** it is `null`
by design — the meaningful move is `setting.change_bp` in the series document, because a rate that
holds for months has no weekly "change". The same rule holds in **`latest.csv`** and in
`series/<id>.json`: a setting reports `change: null` everywhere, so the four published copies of that
field can never disagree.

### `GET /series/<id>.json` — full history of one indicator

`<id>` is any `id` from the catalogue (`cpi`, `repo`, `crr`, `usdinr`, …).

```json
{
  "meta": { "...": "..." },
  "indicator": {
    "id": "crr", "label": "Cash Reserve Ratio", "unit": "%",
    "kind": "setting", "frequency": "weekly",
    "status": "good", "status_reason": "a 25bp cut on 2025-12-05 took it from 3.25% to 3.00%; ...",
    "series": "crr", "source": "RBI r10",
    "latest": { "date": "2026-10-09", "value": 3.0, "change": null },
    "setting": { "effective_from": "2025-12-05", "previous": 3.25, "change_bp": -25.0 },
    "points":  [["2011-04-01", 6.0], "…", ["2026-10-09", 3.0]],
    "history": [{"date": "2025-12-05", "value": 3.0, "previous": 3.25, "prev": 3.25, "change": -25.0}],
    "history_kind": "setting",
    "history_note": "811 published rows in the source table; the setting changed 15 time(s) in that window, the newest 14 are listed",
    "definition": { "term": "Cash Reserve Ratio (CRR)", "definition": "…",
                    "source_name": "RBI Master Direction — CRR and SLR Directions, 2021",
                    "source_url": "https://www.rbi.org.in/Scripts/BS_ViewMasDirections.aspx?id=12131" }
  }
}
```

- **`points`** — every stored observation, oldest first, `[ISO date, numeric value]`. A **setting**
  keeps its whole fetched history (the weekly `Ratios and Rates` table goes back to 2011): the change
  that put the current value in force has to be inside the document, and `effective_from` has to be a
  date the document actually contains.
- **`history`** — newest first, at most 14 rows for a **setting** and 20 for a **reading**. For a
  setting it is the change log (`date`, `value`, `previous`, `change` in basis points): *which rate
  prevailed from which date*. For a reading it is the observations with the step from the previous one.
  `previous` is the documented key; `prev` carries the same value as a compatibility alias.
- **`frequency`** — derived from the median gap between observations: `daily`, `weekly`,
  `fortnightly`, `monthly`, `quarterly`, `irregular`.
- **`stale` / `stale_days`** — the source table has published nothing newer for this line. When
  `stale` is true, treat `latest.date` as the last reported date, not as "now".

### `GET /series/<id>.csv` — the same history as CSV

```csv
date,value
2014-01-31,8.53
2014-02-28,7.75
```

(Compressed to one row per observation — no metadata rows, so `pandas.read_csv` works unmodified.)

### `GET /latest.csv` — the whole scoreboard as CSV

`id,label,value,unit,date,status,change` — one row per indicator.

### `GET /settings.json` — policy settings and when they took effect

```json
{ "meta": { "...": "..." },
  "settings": [
    { "id": "crr", "label": "Cash Reserve Ratio", "unit": "%", "value": 3.0,
      "as_published": "2026-10-02", "effective_from": "2025-12-05",
      "previous": 3.25, "change_bp": -25.0, "unchanged_in_window": false,
      "history": [ "...the change history, newest first..." ],
      "source": "RBI r10" }
  ] }
```

`as_published` is the newest row of the source table that repeats the setting;
**`effective_from` is when the value actually took effect** — use that one for any “since when?” logic.

If `unchanged_in_window` is `true`, the setting did not change anywhere inside the fetched history, so
`effective_from` is the **earliest observation held** (the window's start) rather than a change date —
for example SLR has been 18.00% throughout. Treat the true change date as "earlier than that". The flag
exists precisely so a consumer never reads the window start as a policy event.

### `GET /snapshot.json` — point-in-time key rates and market prices

The portal's own key-rates set plus the weekly market prices, each row carrying its own date and
source label (`key rates` / `weekly WSS`), because the two are different vintages and must not be
silently compared. Settings carry `in force since` semantics via `since`.

### `GET /dataset.json` — everything in one document

(see below) It also carries **`cross_checks`** at the top level: for each indicator whose headline is
derived rather than published, the largest divergence between the derived and the published series, the
month it occurred, and the tolerance the build enforces. Example:

```json
"cross_checks": [{ "indicator": "cpi", "computed_series": "cpi_yoy",
                   "published_series": "cpi_yoy_official", "months_compared": 9,
                   "max_abs_diff_pp": 0.05, "worst_month": "2026-02-28",
                   "published": 3.21, "computed": 3.26, "tolerance_pp": 0.1,
                   "note": "The published figure is quoted on the headline; the index-derived series is
                            the long history drawn on the chart..." }]
```

The CPI indicator (`series/cpi.json`) also carries `series` = `cpi_yoy_official` (the published series,
which the headline uses) while `series/cpi_yoy` remains available in `dataset.json` as the longer derived
history.

### `GET /definitions.json` — sourced definitions

33 terms, each with the publisher's own wording and a source URL. Nothing here is written from memory.

### `GET /dataset.json` — everything in one document

The catalogue, every series' points and history, the snapshot and the definitions. Convenient for a
one-shot fetch or an offline cache; ~1 MB, so prefer the smaller endpoints for frequent polling.

### `GET /status.json` — freshness and change detection

```json
{ "generated_at": "2026-10-17T16:17:15Z",
  "dataset_sha256": "4b3592bd99a92bc4...",
  "files": 86, "bytes": 1157384, "series_points": 7697,
  "counts": { "good": 14, "watch": 16, "bad": 8 },
  "verdict": "Stress signals in core indicators" }
```

`dataset_as_of` is the newest **observation** in the dataset, not the time it was fetched, and
`dataset_as_of_by_frequency` breaks that down by publication calendar. A single date is misleading here:
the tables publish daily (liquidity operations), weekly (the statistical supplement), fortnightly (SCB
returns) and monthly (prices), so the newest observation always belongs to the fastest table. Use the
per-frequency map — or an individual indicator's `latest.date` — when "how fresh is this number?" matters.

Each entry reports the vintage of that series' **own source table**. A series that appends a fresher point
from a faster feed — `usdinr` carries the weekly table plus the portal's daily FBIL rate — does not move
the weekly calendar forward, so `weekly` always means the newest weekly statement.

`dataset_sha256` hashes the data-bearing content **excluding timestamps**, so a client (or the
workflow itself) can tell whether anything actually changed by polling this one small file.

`project_version` is the release that built these files (matching `CHANGELOG.md` and the git tag), so you
can confirm which build a deployment is serving without diffing hashes.

### `GET /manifest.json` — integrity

Every published file with its `bytes` and `sha256`. Verify a cached copy, or fetch selectively.

### `GET /schema/*.schema.json` — JSON Schemas

`index.schema.json`, `latest.schema.json`, `series.schema.json` (JSON Schema 2020-12). Validate your
parsing against these; CI runs `tools/validate_api.py`, which enforces them plus cross-document
consistency — including `settings.json`, `snapshot.json` and `dataset.json`, the `unit`/`label`/`status`
fields, every point's type and date, every CSV row against its series, and `status.json`'s own counts.

## Recipes

```bash
# a change-detection loop: only re-download when the dataset hash moves
sha=$(curl -s $BASE/status.json | jq -r .dataset_sha256); echo "$sha"

# every indicator whose reading is currently in stress
curl -s $BASE/latest.json | jq -r '.latest | to_entries[] | select(.value.status=="bad") | "\(.key)\t\(.value.value)"'

# the yield-curve term spread over time, as CSV
curl -s $BASE/series/termspread.csv

# the repo rate's full change history
curl -s $BASE/settings.json | jq '.settings[] | select(.id=="repo") | .history'
```

## Versioning and stability

- The path is versioned (`/api/v1/`). **Within `v1`, existing fields keep their names, types and
  meaning**; new fields may be added, so parse leniently (`json["latest"].get(...)`).
- Removing a field, renaming one, or changing a unit means a new directory (`/api/v2/`) and a note in
  [CHANGELOG.md](../CHANGELOG.md). The old version keeps being published for at least one release
  cycle.
- Indicator `id`s are stable. If an indicator is retired, its id stops being listed in the catalogue
  but is documented in the changelog.
- `meta.api_version` restates the version inside every document.

## Limits, terms and attribution

- GitHub's raw/CDN endpoints are unmetered for normal use but are not an SLA; for high-volume or
  commercial use, mirror the files to your own bucket (the whole API is ~1.1 MB) or pin a commit and
  cache it.
- Data is compiled from **RBI public publications**. It is **not** an RBI product, may be revised by
  the publisher, and should be verified at [data.rbi.org.in](https://data.rbi.org.in/) before it is
  relied on. Attribution: *Reserve Bank of India — Database on Indian Economy*.
- Derived figures (growth rates, spreads, averages, the money multiplier) are computed by this
  project; see [METHODOLOGY.md](METHODOLOGY.md) for the exact arithmetic, and cite this repository if
  you use them.
